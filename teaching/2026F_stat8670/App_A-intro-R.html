2  Appendix: Introduction to R

2.1 Why R?

Modern statistical analyses routinely involve hundreds, thousands, or millions of observations. The calculations are too numerous—and often too complex—to perform reliably by hand. We therefore need software that can manage data, implement statistical methods, automate repeated computations, and document the complete analysis.

R is both a high-level programming language and an environment for statistical computing and graphics. It is especially useful for statistics because it is:

  • free and open source, so students and researchers can use the same tools;
  • designed for data analysis, with vectors, missing values, models, and graphics built into the language;
  • extensible, with a large ecosystem of packages developed by researchers and software developers;
  • reproducible, because an analysis can be saved as code and rerun from beginning to end;
  • interoperable, with interfaces to databases and languages such as C++, Python, and Julia.

R is not a menu-driven statistics program. Learning R means learning to express an analysis as a sequence of precise, inspectable computations. That initial investment pays off when an analysis must be revised, repeated, validated, or shared.

NoteR, RStudio, and Quarto are different tools

R performs the computation. RStudio is an integrated development environment that helps us write and run code. Quarto turns source documents containing prose, code, and results into HTML, PDF, Word, or presentation output.

2.2 The working environment

2.2.1 RStudio

RStudio is an integrated development environment (IDE) for R, Python, and reproducible publishing. Its default layout contains four panes:

Pane Main purpose
Source Write and edit scripts and Quarto documents.
Console Send expressions directly to R and view immediate results.
Environment/History Inspect names in the global environment and review console commands.
Files/Plots/Packages/Help/Viewer Navigate files, inspect graphics, manage packages, read documentation, and preview output.

Use the console for short experiments. Put any computation that matters in a script or Quarto document so it can be rerun.

2.2.2 R scripts and Quarto documents

An R script is a plain-text file with the extension .R. It contains R expressions that can be executed one line, one selection, or one file at a time.

A Quarto document has the extension .qmd. It combines:

  • a YAML header describing the document;
  • prose written in Markdown;
  • executable code chunks;
  • tables, equations, figures, citations, and cross-references.

For example, an executable R chunk begins with ```{r} and ends with ```. Rendering the document starts a computation, runs the enabled chunks in order, and places their results into the output. This makes the narrative and the computation part of the same reproducible record.

2.2.3 A project-oriented workflow

Create one RStudio Project for the course or for each substantial analysis. Use project-relative paths such as data/survey.csv rather than hard-coded paths tied to one computer. A simple project might contain:

stat8670-project/
├── data/          # original and processed data
├── R/             # reusable functions
├── figures/       # saved figures
├── notes/         # Quarto lecture or analysis files
└── stat8670-project.Rproj

Avoid using setwd() inside a reproducible document. When a project is opened, its root provides a stable reference point for relative paths.

2.3 Learning objectives

By the end of this lecture, you should be able to:

  1. Describe how R reads, evaluates, and prints an expression.
  2. Distinguish an object from the name bound to that object.
  3. Predict how vectorization, coercion, recycling, and missing values affect a computation.
  4. Explain how function calls, environments, lexical scoping, and lazy evaluation work.
  5. Describe R’s copy-on-modify memory model and its implications for performance.
  6. Create, inspect, subset, and transform data frames and tibbles.
  7. Choose appropriately among apply(), lapply(), vapply(), grouped operations, and vectorized functions.
  8. Use the tidyverse pipe and core dplyr verbs to express a data-analysis pipeline.
  9. Write small computations that are reproducible, testable, and numerically responsible.

2.4 R as a computing environment

R is both a programming language and an interactive environment for statistical computing. It provides:

  • a parser that turns text into expressions;
  • an evaluator that computes the value of an expression;
  • a workspace containing objects and functions;
  • a package system for extending the language;
  • graphics, statistical models, simulation tools, and interfaces to compiled code.

At the console, R follows a read–evaluate–print loop (REPL):

  1. Read: parse the text entered by the user.
  2. Evaluate: compute the value of the expression in the current environment.
  3. Print: display the result when it is visible.
  4. Loop: wait for the next expression.
2 + 3 * 4
[1] 14

R respects operator precedence, so multiplication is performed before addition. Parentheses make the intended order explicit.

(2 + 3) * 4
[1] 20

Assignment usually returns its value invisibly, so the first line below does not print a result. Typing the name on the next line retrieves and prints the value.

x <- 2 + 3 * 4
x
[1] 14
TipA useful mental model

Most R code can be understood as function calls that produce objects. Even an operator such as + is a function.

`+`(2, 3)
[1] 5

2.5 Expressions, objects, and names

R computes with objects. Numbers, character strings, vectors, data frames, fitted models, and functions are all objects. A name is a symbol bound to an object in an environment.

sample_size <- 100
another_name <- sample_size

sample_size
[1] 100
another_name
[1] 100

The assignment operator <- creates or changes a binding. It is read as “gets.” Although = can also assign in many contexts, using <- for ordinary assignment makes code easier to read because = is also used to match function arguments.

Names are case-sensitive:

n <- 10
N <- 25
c(n = n, N = N)
 n  N 
10 25

Use ls() to list names in the current environment and rm() to remove a binding.

temporary_result <- 42
"temporary_result" %in% ls()
[1] TRUE
rm(temporary_result)
"temporary_result" %in% ls()
[1] FALSE

Removing a name does not necessarily destroy an object immediately. R reclaims unreachable memory through garbage collection.

2.6 Atomic vectors: the basic unit of computation

The fundamental data structure in R is the vector. An atomic vector contains zero or more elements of one type. Common atomic types include:

Type Example Typical use
logical TRUE, FALSE conditions and indicators
integer 2L counts and indices
double 2, 3.14 numerical computation
character "R" text and labels
complex 1 + 2i complex arithmetic
raw charToRaw("R") bytes 
logical_vector <- c(TRUE, FALSE, TRUE)
integer_vector <- c(1L, 2L, 3L)
double_vector <- c(1, 2, 3)
character_vector <- c("one", "two", "three")

typeof(logical_vector)
[1] "logical"
typeof(integer_vector)
[1] "integer"
typeof(double_vector)
[1] "double"
typeof(character_vector)
[1] "character"

2.6.1 Vectorization

Many R functions and operators act on an entire vector. This is called vectorized computation.

x <- c(1, 2, 3, 4)
x^2
[1]  1  4  9 16
sqrt(x)
[1] 1.000000 1.414214 1.732051 2.000000
sum(x)
[1] 10
mean(x)
[1] 2.5

Vectorized code often expresses the statistical operation more directly than element-by-element code. It may also be faster because much of the work is implemented in compiled code.

2.6.2 Element-wise operations and recycling

Arithmetic between vectors is usually element-wise.

x <- c(10, 20, 30)
y <- c(1, 2, 3)
x + y
[1] 11 22 33

If one vector is shorter, R repeats—or recycles—its values.

x + 5
[1] 15 25 35
c(10, 20, 30, 40) + c(1, 2)
[1] 11 22 31 42

Recycling is useful when the shorter length divides the longer length exactly. Otherwise, R warns because the result may reflect a mistake.

c(10, 20, 30, 40) + c(1, 2, 3)
Warning in c(10, 20, 30, 40) + c(1, 2, 3): longer object length is not a
multiple of shorter object length
[1] 11 22 33 41

2.6.3 Coercion

An atomic vector must have one type. When incompatible types are combined, R finds a common type and coerces the values.

mixed_numeric <- c(TRUE, 2L, 3.5)
mixed_character <- c(TRUE, 2L, 3.5, "four")

mixed_numeric
[1] 1.0 2.0 3.5
typeof(mixed_numeric)
[1] "double"
mixed_character
[1] "TRUE" "2"    "3.5"  "four"
typeof(mixed_character)
[1] "character"

A simplified coercion hierarchy is:

logical → integer → double → complex → character

Implicit coercion is convenient, but accidental coercion can silently change a computation. Inspect unfamiliar objects with typeof(), class(), length(), and str().

2.7 Missing and special numerical values

R uses NA for a missing value. Because an unknown value usually makes a calculation unknown, NA propagates.

scores <- c(88, NA, 91, 84)
mean(scores)
[1] NA
mean(scores, na.rm = TRUE)
[1] 87.66667
is.na(scores)
[1] FALSE  TRUE FALSE FALSE

Do not test missingness with x == NA; use is.na(x).

Other special numerical values include positive and negative infinity and “not a number.”

c(1 / 0, -1 / 0, 0 / 0)
[1]  Inf -Inf  NaN
is.finite(c(1, Inf, NA, NaN))
[1]  TRUE FALSE FALSE FALSE

NaN represents an undefined numerical result and is also treated as missing by is.na().

Three-valued logic matters when conditions contain missing values:

c(TRUE & NA, FALSE & NA, TRUE | NA, FALSE | NA)
[1]    NA FALSE  TRUE    NA

2.8 Indexing and subsetting

R offers several ways to select elements. For a vector x:

  • positive integers select positions;
  • negative integers exclude positions;
  • logical vectors retain positions that are TRUE;
  • character vectors select named elements.
x <- c(first = 10, second = 20, third = 30, fourth = 40)

x[c(1, 3)]
first third 
   10    30 
x[-2]
 first  third fourth 
    10     30     40 
x[x >= 30]
 third fourth 
    30     40 
x[c("second", "fourth")]
second fourth 
    20     40

Indices begin at 1, not 0. Mixing positive and negative indices in the same subscript is an error.

WarningA common surprise

1:length(x) behaves badly when x has length zero. Prefer seq_along(x) when iterating over positions and seq_len(n) when iterating to a known length.

empty <- numeric(0)
1:length(empty)
[1] 1 0
seq_along(empty)
integer(0)

2.9 Data structures are vectors plus attributes

Many R data structures are constructed by attaching attributes to vectors.

2.9.1 Matrices

A matrix is an atomic vector with a dim attribute. Its elements must have one common type.

A <- matrix(1:6, nrow = 2, ncol = 3)
A
     [,1] [,2] [,3]
[1,]    1    3    5
[2,]    2    4    6
attributes(A)
$dim
[1] 2 3
A[2, 3]
[1] 6

Matrix multiplication uses %*%; * performs element-wise multiplication.

B <- matrix(c(1, 0, 0, 1, 1, 1), nrow = 3)
A %*% B
     [,1] [,2]
[1,]    1    9
[2,]    2   12

2.9.2 Lists

A list is a vector whose elements may be objects of different types and lengths.

fit_summary <- list(
  method = "least squares",
  coefficients = c(intercept = 1.2, slope = 0.8),
  converged = TRUE
)

str(fit_summary)
List of 3
 $ method      : chr "least squares"
 $ coefficients: Named num [1:2] 1.2 0.8
  ..- attr(*, "names")= chr [1:2] "intercept" "slope"
 $ converged   : logi TRUE
fit_summary[["coefficients"]]
intercept     slope 
      1.2       0.8 
fit_summary$coefficients
intercept     slope 
      1.2       0.8

For a list, [ returns a sublist, whereas [[ extracts a single element.

fit_summary["coefficients"]
$coefficients
intercept     slope 
      1.2       0.8 
fit_summary[["coefficients"]]
intercept     slope 
      1.2       0.8

2.9.3 Factors

A factor represents categorical data using integer codes plus a levels attribute.

group <- factor(c("control", "treatment", "control"))
group
[1] control   treatment control  
Levels: control treatment
unclass(group)
[1] 1 2 1
attr(,"levels")
[1] "control"   "treatment"
levels(group)
[1] "control"   "treatment"

The order of factor levels can affect model coefficients and printed summaries, so set levels deliberately when their order matters.

2.10 Data frames: R’s rectangular data structure

A data frame stores a rectangular data set. Conceptually, it is a named list of equal-length vectors:

  • each row represents an observational unit;
  • each column represents a variable;
  • every column has the same number of observations;
  • different columns may have different types.

This last property distinguishes a data frame from a matrix. A matrix is one atomic vector with dimensions, so every entry must have the same type. A data frame is a list of columns, so numerical, character, logical, factor, and date variables can coexist.

2.10.1 Creating a data frame

students <- data.frame(
  id = 1:6,
  name = c("Alice", "Bob", "Chen", "Divya", "Elena", "Farah"),
  program = c("MS", "PhD", "MS", "PhD", "MS", "PhD"),
  score = c(90, 85, NA, 94, 88, 91),
  completed = c(TRUE, TRUE, FALSE, TRUE, TRUE, TRUE)
)

students

1  1 Alice      MS    90      TRUE
2  2   Bob     PhD    85      TRUE
3  3  Chen      MS    NA     FALSE
4  4 Divya     PhD    94      TRUE
5  5 Elena      MS    88      TRUE
6  6 Farah     PhD    91      TRUE

Each expression passed to data.frame() becomes a column. R recycles a length-one value, but other columns should normally have matching lengths.

There are three common column-extraction operators:

students["score"]       # a one-column data frame
  score
1    90
2    85
3    NA
4    94
5    88

students[["score"]]     # the underlying vector
[1] 90 85 NA 94 88 91

Use [[ inside functions when the column name is stored in another object.

variable <- "score"
mean(students[[variable]], na.rm = TRUE)
[1] 89.6

2.10.4 Adding and modifying variables

Because each column is a vector, vectorized calculations naturally create new variables.

students$passed <- students$score >= 70
students$centered_score <- students$score - mean(students$score, na.rm = TRUE)
students
  id  name program score completed passed centered_score
1  1 Alice      MS    90      TRUE   TRUE            0.4
2  2   Bob     PhD    85      TRUE   TRUE           -4.6
3  3  Chen      MS    NA     FALSE     NA             NA
4  4 Divya     PhD    94      TRUE   TRUE            4.4
5  5 Elena      MS    88      TRUE   TRUE           -1.6
6  6 Farah     PhD    91      TRUE   TRUE            1.4

Missingness propagates: the student with an unknown score also has an unknown value of passed. This is different from FALSE; we do not know whether that student passed.

2.10.5 Importing rectangular data

Base R provides read.csv() and read.table() for delimited text files.

survey <- read.csv(
  "data/survey.csv",
  na.strings = c("", "NA", ".")
)

measurements <- read.table(
  "data/measurements.txt",
  header = TRUE,
  sep = "\t"
)

Use project-relative paths. Immediately after importing, check the dimensions, names, types, missingness, and several observations.

dim(survey)
names(survey)
str(survey)
head(survey)
colSums(is.na(survey))
NoteData import is part of the analysis

Import is not merely clerical. Delimiters, decimal marks, missing-value codes, encodings, date formats, and inferred column types can change the data R sees—and therefore the analysis.

WarningDo not treat a data frame as a matrix

as.matrix() and apply() may coerce an entire mixed-type data frame to a character matrix. Perform column-wise operations on the original columns with lapply(), vapply(), or dplyr::across() instead.

2.11.2 Pipes and data verbs

The native pipe |> sends the result on its left to the first argument of the function on its right. It lets us read a transformation in the order it occurs.

students_tbl |>
  filter(completed, !is.na(score)) |>
  select(name, program, score) |>
  arrange(desc(score))
# A tibble: 5 × 3
  name  program score
  <chr> <chr>   <dbl>
1 Divya PhD        94
2 Farah PhD        91
3 Alice MS         90
4 Elena MS         88
5 Bob   PhD        85

Core dplyr verbs have a consistent grammar:

Verb Purpose
select() Choose, rename, or reorder columns
filter() Keep rows satisfying logical conditions
arrange() Sort rows
mutate() Create or modify columns
summarise() Reduce observations to summary values
group_by() Define groups for subsequent operations

For example, create variables and then compute group-specific summaries:

students_tbl |>
  mutate(
    passed = score >= 70,
    score_z = (score - mean(score, na.rm = TRUE)) /
      sd(score, na.rm = TRUE)
  ) |>
  group_by(program) |>
  summarise(
    n = n(),
    n_observed = sum(!is.na(score)),
    mean_score = mean(score, na.rm = TRUE),
    sd_score = sd(score, na.rm = TRUE),
    .groups = "drop"
  )
# A tibble: 2 × 5
  program     n n_observed mean_score sd_score
  <chr>   <int>      <int>      <dbl>    <dbl>
1 MS          3          2         89     1.41
2 PhD         3          3         90     4.58

Grouping changes how later verbs operate. It does not rearrange the rows, and the grouping state can persist. Use .groups = "drop" in summarise() or ungroup() when subsequent operations should apply to the full data.

2.11.3 Operating across several columns

Inside mutate() or summarise(), across() applies one or more functions to a selection of columns.

students_tbl |>
  summarise(
    across(
      where(is.numeric),
      list(mean = ~ mean(.x, na.rm = TRUE),
           sd = ~ sd(.x, na.rm = TRUE)),
      .names = "{.col}_{.fn}"
    )
  )
# A tibble: 1 × 6
  id_mean id_sd score_mean score_sd centered_score_mean centered_score_sd
    <dbl> <dbl>      <dbl>    <dbl>               <dbl>             <dbl>
1     3.5  1.87       89.6     3.36            5.86e-15              3.36

across() is often the tidyverse counterpart to a column-wise lapply() or vapply(), with the additional advantage that it works inside grouped data operations.

2.11.4 Base R and tidyverse are complementary

The same task can be expressed in more than one style.

# Base R
aggregate(score ~ program, data = students, FUN = mean, na.rm = TRUE)
  program score
1      MS    89
2     PhD    90
# tidyverse
students_tbl |>
  group_by(program) |>
  summarise(mean_score = mean(score, na.rm = TRUE), .groups = "drop")
# A tibble: 2 × 2
  program mean_score
  <chr>        <dbl>
1 MS              89
2 PhD             90

Choose a style that makes the operation clear and use it consistently within a pipeline. Regardless of syntax, the underlying questions remain the same: What object enters the function? What object comes out? How are missing values handled? Are types and groups preserved?

2.12 Functions and function calls

A function packages a computation so it can be reused and tested.

standardize <- function(x, remove_na = FALSE) {
  center <- mean(x, na.rm = remove_na)
  spread <- sd(x, na.rm = remove_na)
  (x - center) / spread
}

standardize(c(2, 4, 6, 8))
[1] -1.1618950 -0.3872983  0.3872983  1.1618950

A function has three main components:

  • formals: its arguments;
  • body: the expression it evaluates;
  • environment: where it was created.
formals(standardize)
$x


$remove_na
[1] FALSE
body(standardize)
{
    center <- mean(x, na.rm = remove_na)
    spread <- sd(x, na.rm = remove_na)
    (x - center)/spread
}

<environment: R_GlobalEnv>

When a function is called, R creates a new temporary environment, binds arguments to values, evaluates the body, and returns the value of the final evaluated expression unless return() is used earlier.

2.12.1 Argument matching

Arguments can be matched by exact name or by position. Exact names are clearest in code that others will read.

round(x = 3.14159, digits = 3)
[1] 3.142
round(3.14159, 3)
[1] 3.142

Avoid partial argument names in durable code; they can be ambiguous and may break if a function changes.

2.12.2 Lazy evaluation

R function arguments are evaluated only when they are needed. This is called lazy evaluation.

choose_one <- function(x, y) {
  x
}

choose_one(10, stop("This argument is never needed"))
[1] 10

Internally, an argument is represented by a promise: the expression supplied by the caller, together with the environment in which that expression should be evaluated. Lazy evaluation enables convenient interfaces, but code with side effects can become harder to reason about.

2.13 Environments and lexical scoping

An environment stores name–object bindings and has a parent environment. When R evaluates a name, it looks in the current environment and then follows the chain of parent environments until it finds a binding or reaches the empty environment.

R uses lexical scoping: a function looks for nonlocal names in the environment where the function was defined, not the environment from which it was called.

make_power <- function(power) {
  function(x) {
    x^power
  }
}

square <- make_power(2)
cube <- make_power(3)

square(5)
[1] 25
cube(5)
[1] 125

Even after make_power() finishes, each returned function retains access to the environment containing its own value of power. A function bundled with its defining environment is often called a closure.

Local assignment normally changes a binding in the current environment.

x <- 100

change_locally <- function() {
  x <- 5
  x
}

change_locally()
[1] 5
x
[1] 100

The superassignment operator <<- searches parent environments and modifies an existing binding. Because this creates nonlocal side effects, use it sparingly and deliberately.

2.14 Memory: copy-on-modify

R behaves as if objects are copied when modified. In practice, two names may initially share memory, and R copies only when a modification would otherwise affect another binding. This is commonly described as copy-on-modify.

x <- c(10, 20, 30)
y <- x
y[1] <- 999

x
[1] 10 20 30
y
[1] 999  20  30

Changing y does not change x. This model makes ordinary R code easier to reason about, but repeatedly growing an object can allocate and copy memory many times.

Avoid this pattern for large computations:

result <- numeric(0)
for (i in seq_len(100000)) {
  result <- c(result, i^2)
}

Preallocate the final size instead:

n <- 100000
result <- numeric(n)

for (i in seq_len(n)) {
  result[i] <- i^2
}

head(result)
[1]  1  4  9 16 25 36

object.size() gives an approximate size of an R object. gc() requests garbage collection and reports memory-use information, although R normally manages garbage collection automatically.

object.size(result)
800048 bytes
NoteImplementation detail: ALTREP

Modern R can represent some vectors compactly and materialize their elements only when necessary. This mechanism, called ALTREP, is one reason an object’s conceptual size and its immediate memory cost need not be identical.

2.15 Iteration: vectorization, loops, and the apply family

An iterative computation can often be expressed in several ways. None is universally best. Choose the form that clearly represents the algorithm and returns a predictable object.

x <- c(2, 4, 6, 8)

# Vectorized operation
x^2
[1]  4 16 36 64
# Explicit, preallocated loop
squares <- numeric(length(x))
for (i in seq_along(x)) {
  squares[i] <- x[i]^2
}
squares
[1]  4 16 36 64
# Function applied to each element
vapply(x, function(value) value^2, numeric(1))
[1]  4 16 36 64

Use vectorization when a vectorized function already expresses the operation. Use a loop when the calculation depends on evolving state or complex indexing. Use an apply-family function when the same function is independently applied to many pieces of an object.

ImportantThe apply family is not magic vectorization

apply() and lapply() usually perform iteration internally. They are not automatically faster than a well-written, preallocated for loop. Their main benefit is expressing “apply this function to each piece” concisely.

2.15.1 apply(): rows or columns of a matrix

apply(X, MARGIN, FUN, ...) applies FUN over dimensions of an array or matrix:

  • MARGIN = 1 operates on rows;
  • MARGIN = 2 operates on columns;
  • MARGIN = c(1, 2) operates on individual cells.

2.15.2 Why apply() can be dangerous for data frames

apply() first converts a data frame to a matrix. If every column is numeric, this can be acceptable. If any column is character, the matrix may become entirely character, making numerical summaries fail or behave unexpectedly.

  id = c("A", "B", "C"),

2.16 Numerical computation is finite-precision computation

Most real numbers cannot be stored exactly in binary floating-point arithmetic.

0.1 + 0.2
[1] 0.3
(0.1 + 0.2) == 0.3
[1] FALSE
all.equal(0.1 + 0.2, 0.3)
[1] TRUE

Use tolerance-based comparisons, such as all.equal(), for computed floating-point values. Numerical algorithms must also consider overflow, underflow, cancellation, conditioning, and convergence—not only algebraic correctness.

A simple example of overflow avoidance is computing a log-likelihood with dbinom(..., log = TRUE) rather than taking the logarithm after a tiny probability has already been rounded to zero.

log(dbinom(500, size = 1000, prob = 0.01))
[1] -Inf
dbinom(500, size = 1000, prob = 0.01, log = TRUE)
[1] -1618.143

2.18 Packages, help, and error messages

Packages extend R with functions, data, and documentation.

Most general-purpose packages are distributed through the Comprehensive R Archive Network (CRAN). Bioconductor distributes packages for bioinformatics and high-throughput biological data, and development versions of some packages are hosted on GitHub.

# CRAN
install.packages("packageName")

# Bioconductor: install BiocManager from CRAN first
BiocManager::install("packageName")

# GitHub: install the remotes package from CRAN first
remotes::install_github("username/repository")

# Load an installed package in the current session
library(packageName)

# Or call one function without attaching the package
packageName::function_name()

Installation changes the R library on the computer and normally happens once. library() makes an installed package available in the current session and must be repeated in each new session that uses it.

Useful ways to investigate an unfamiliar function include:

?mean
help("mean")
example(mean)
args(mean)
methods(mean)

When an error occurs:

  1. Read the entire message.
  2. Reduce the problem to the smallest input that still fails.
  3. Inspect object structures and dimensions with str(), typeof(), class(), and dim().
  4. Check the most recent calls with traceback() after an error.
  5. Verify assumptions explicitly with stopifnot().
safe_mean <- function(x) {
  stopifnot(is.numeric(x), length(x) > 0)
  mean(x)
}

safe_mean(c(2, 4, 6))
[1] 4

2.19 A computational workflow for this course

A reliable statistical computation separates the following concerns:

  1. Inputs: raw data, constants, configuration, and seeds.
  2. Transformation: cleaning and construction of analysis variables.
  3. Computation: algorithms, models, optimization, or simulation.
  4. Validation: diagnostics, invariants, tests, and sensitivity checks.
  5. Communication: tables, graphics, interpretation, and limitations.

Prefer scripts and Quarto documents over a sequence of unrecorded console commands. A clean R session should be able to run the analysis from beginning to end. Do not rely on objects left over from earlier experimentation.

# A small, reproducible computation
set.seed(8670)

n <- 200
x <- rnorm(n)
y <- 1 + 2 * x + rnorm(n, sd = 0.75)
simulated_data <- data.frame(x = x, y = y)

fit <- lm(y ~ x, data = simulated_data)
coef(fit)
(Intercept)           x 
   1.020794    1.991843

The code states where the data came from, fixes the random seed, stores the data in an explicit object, and passes that object to the model.

2.21 Takeaways

  • R evaluates expressions in environments and binds names to objects.
  • Atomic vectors are the foundation of R computation; vectorization, coercion, and recycling follow from this design.
  • Lists, matrices, factors, and data frames build on vectors and attributes.
  • A data frame is a named list of equal-length columns; a tibble is a stricter, modern data frame.
  • dplyr expresses row, column, transformation, and grouped-summary operations as a readable pipeline.
  • Functions are objects with arguments, a body, and a defining environment; R uses lexical scoping and lazy evaluation.
  • The apply family expresses repeated operations, but the input structure and promised output type determine which member is appropriate.
  • apply() is designed for arrays and matrices; using it on a mixed-type data frame can trigger unwanted coercion.
  • R’s copy-on-modify behavior favors clear semantics, but allocation patterns still matter for performance.
  • Statistical computing requires attention to missing values, floating-point arithmetic, random-number state, and reproducibility.
  • Understanding R’s computational model makes code easier to predict, debug, optimize, and trust.
